## 1. 依頼の目的

v1を土台に、卒業制作の提出物と6分発表の補助資料を兼ねるWebページへ更新してください。
聞き手は、この空き家事業を初めて知る一般の人です。専門用語を並べず、問題、作ったもの、
工夫、学びの順に読めば全体像が分かる構成にしてください。

作品は次の二本立てです。

1. 作品1: 空き家ウォッチャー
2. 作品2: 仕入れ点エンジン

作品2は「次の計画」ではなく、実装・本番稼働済みの完成作品として扱ってください。
一人称は「私」で統一し、v1の落ち着いたトーンを保ちます。実績を大きく見せる表現や、
確認できない数字は使わないでください。

## 2. 技術・デザイン上の前提

- 提出形式はURLで開くWebページです。
- 1つのHTMLファイルだけで完結させてください。
- CDN、Webフォント、外部画像、外部CSS、外部JavaScriptを読み込まないでください。
- JavaScriptは使わず、HTMLとインラインCSSだけで作ってください。
- フォントは端末のシステムフォントを使ってください。
- ライトテーマとダークテーマの両方に対応してください。`prefers-color-scheme`による
  自動切替で構いません。
- スマートフォンで先に確認してください。横スクロール、極小文字、2列の詰め込みを避けます。
- v1の色調、余白、カード、メールモックの雰囲気は引き継いで構いません。
- 装飾より読み順を優先してください。6分発表中に画面を追える情報量にします。
- 個人情報、実在する物件名、番地、電話番号、実在物件を特定できるURLは入れません。

## 4. 作品1 — 空き家ウォッチャー

### 4.1 一般向けの説明

鹿児島県内などの自治体空き家バンク、RSS、公式通知メールをクラウドで1日4〜6回巡回し、
新着、値下げ、掲載終了などの変化を見つけます。結果は1回の巡回につき最大1通のメールに
まとめます。条件だけで機械的に合否を決めず、台帳に残して最後は私が選びます。

流れは次の4段階で見せてください。

1. 集める: 市町村ごとに異なるサイトを19の情報源として接続
2. 比べる: 前回の巡回との差から新着、値下げ、掲載終了を判定
3. 評価する: 物件の特徴、立地、仕入れ点を付ける
4. 届ける: 重要な順に1通へまとめ、台帳レポートも添付

### 4.2 2026-08-04時点の数字

v1にある「16情報源・56件・162テスト」は、次の数字へ更新してください。

| 指標 | v2で使う数字 | 根拠 |
|---|---:|---|
| 有効な情報源 | **19** | `config.yaml`の`enabled: true`を数えた実数 |
| 監視中の物件 | **103件** | 2026-08-04の本番巡回ログ。地域・価格の足切りと重複処理後 |
| 自動テスト | **203件、全件成功** | `NEXT.md`の2026-08-03時点の本番反映済み記録 |
| 自動巡回 | **1日4〜6回** | GitHub Actionsの本番スケジュール |
| リサーチ範囲 | **24市町村** | `config.yaml`の`criteria.target_areas` |
| 価格上限 | **300万円** | ユーザーが決めた収集条件 |
| 1巡回の通知 | **最大1通** | `notify.bundle: true` |

数字には「2026年8月4日時点」と添えてください。取得件数の合計と監視件数は違います。
監視103件は、取得後に対象地域、300万円上限、重複などを処理したあとの件数です。

「9市町」「半年運用」など、現在の根拠と合わないv1の表現はそのまま残さないでください。
運用開始時期を具体的に示す必要がある場合は「要確認」と書いてください。

## 5. 作品2 — 仕入れ点エンジン

### 5.1 何をする作品か

`akiya_watcher/ai_reader.py`が、物件の説明文と値下げ・掲載期間の履歴から、
「売主がこの家を手放したがっている気配」を0〜100点で採点します。高得点ほど、
「残置物ごと、安く買いたい」という交渉が通りやすい可能性がある、という判断材料です。
売主の事情を断定する点数ではありません。

### 5.2 実装済みの採点表

| シグナル | 点数 |
|---|---:|
| 残置物・家財・現状渡し | +25 |
| 相続の気配 | +15 |
| 遠方管理の気配 | +15 |
| 売り急ぎ・処分の表現 | +10 |
| 蔵・納屋・倉庫などの付属建物 | +10 |
| リフォーム・改装・清掃済み | -15 |
| 値下げ履歴 | 最大+20 |
| 長期掲載90日以上 | +10 |
| 長期掲載180日以上 | +15 |

点数は0〜100に収め、通知には点数と強い理由を最大3つ表示します。図解では、文章中の
キーワードと履歴が点数へ変わる様子を、簡単な採点例で見せてください。採点例も架空にします。

### 5.3 方向転換の物語

当初はLLM APIで物件説明を採点する計画でした。しかし、無料・APIキー不要で運用する条件が
あり、GitHub Modelsの無料推論を実地テストしました。結果はHTTP 410の
`retirement brownout`で、サービス廃止が進んでいると判明しました。

そこで、AIとの対話と実際の物件検討で得た判断基準を、重み付きルールとしてコードに
焼き付けました。最終形には次の利点があります。

- 運用費がかからない
- 同じ入力には同じ答えが出る
- 自動テストを書ける
- 外部サービスが終了しても動く

「LLMが物件を毎回読んでいる」と誤解させる表現は避けてください。AIとの対話で判断基準を
作り、その基準を通常のPythonコードとして残した作品です。

## 6. メールのモック

実際の`format_message()`と同じ行構成で、完全な架空データを使って再現してください。
モックの近くに、はっきり**「※以下はすべて架空データです」**と表示します。

表示例:

```text
🏠 巡回まとめ: 値下げ1件(最大▼50%)・新着1件

🔻 値下げ検知 (▼50%) [評価 8/10]
物件名: 【架空】みどり野市 空き家バンク No.F-012
価格: 2,400,000円 → 1,200,000円
所在地: 鹿児島県みどり野市山あい町（架空）
立地: 国分から車およそ45分 ○60分圏
周辺: 架空小学校まで1.2km・架空スーパーまで2.0km
仕入れ点: 75/100 (残置物・現状渡しの文言、相続の気配、遠方管理の気配)
地図: https://www.google.com/maps/search/?api=1&query=架空住所
シグナル: 🪑残置物 🏺蔵・旧家 🚗2台
要確認: トイレ形式、接道
URL: https://example.invalid/fictional-property
⭐この物件をキープ（タップ→開いたメールをそのまま送信）
```

メールモックでは、次の行を省かないでください。

- 物件名
- 価格
- 所在地
- 立地
- 周辺
- 仕入れ点
- 地図
- シグナル
- 要確認
- URL
- ⭐キープリンク

実在する自治体名に見える架空名、実在する番地、既存の物件番号、実在物件のURLは使わないで
ください。リンクを見た目として示す場合は、予約済みの`.invalid`ドメインなどを使います。

## 7. 工夫セクションへ追加する内容

### メール1タップ⭐キープ

通知メールは読むだけの出口ではなく、操作の入口にもなりました。「⭐この物件をキープ」を
タップすると、件名が`keep`、本文が物件URLの自分宛てメールが開きます。私が送信すると、
次の巡回から値下げ、記載変更、掲載終了を追跡します。

keepメールそのものを正本にしているため、クラウド側の一時データが消えても、過去365日分の
keepメールを読み直して追跡リストを復元できます。これを「Gmailが正本なので自己修復する設計」
として説明してください。AIがGmailへログインして操作する仕組みではなく、送信するかどうかは
私が決めます。

既存の工夫も残してください。

- 重要通知、低評価新着の1行表示、全量台帳の三層設計
- 同じ物件を繰り返さないための🆕/（既出）表示
- 国分から車およそ何分かを無料で概算
- 自動取得禁止の官報はリンク生成までに留める
- 「偵察→実装→実地検証」で思い込みを実験から潰す

## 8. 新セクション — 武器を磨き続ける仕組み

見出しは**「武器を磨き続ける仕組み — 1人+AIチームの運営」**としてください。

### 8.1 チーム体制

| 役割 | 担当 |
|---|---|
| 相談役、元・本番の番人 | Claude |
| メイン開発者、本番の番人 | Codex |
| デザイン | Cursor |
| 全pushを自動テストする審判 | 機械の番人（GitHub Actions） |

人間である私は、何を作るか、どの物件を見るか、本番へ入れるかを決めます。AI同士だけで
勝手に方針や本番を変える体制ではありません。

### 8.2 チームを支える三つの道具

- `AGENTS.md`: 全AIが守る共通ルールブック
- `docs/NEXT.md`: 経緯、判断、次の仕事を残す共有の記憶
- `docs/本番反映手順書.md`: 検品、テスト、反映、巻き戻しの手順

AIツールが替わっても、この三つを読めば同じ判断基準で仕事を再開できます。

### 8.3 美化しない実話

Codexの初仕事では、コードとテストを完成させたあと、pushせずに完了報告を2回しました。
成果はローカルPCにしかなく、GitHubには存在しませんでした。

そこで`AGENTS.md`へ、次の完了条件を追加しました。

> 完了 = commit + push + コミットハッシュの報告

さらに全pushで自動テストを動かし、人間がコミットと緑の結果を確認できる形にしました。
この失敗を成功談へ言い換えたり、「最初から安全に運用できた」と書いたりしないでください。
教訓は次の一文です。

> AIに任せるとは、AIを信じ切ることではない。人間が確認できる仕組みを作ること。

### 8.4 本番の安全網

- 巡回はGitHub Actions上で自走し、どのAIが閉じていても止まらない
- 全pushで自動テストを実行し、赤い変更は本番へ入れない
- 定期便を1日1通送るため、**メールが来ない日=壊れた日**と分かる
- 壊れた場合は、本番反映手順書に沿って直前の変更を巻き戻す

### 8.5 このセクションの締め

次の趣旨で締めてください。文面はページ全体のトーンに合わせて整えて構いません。

> ツールは入れ替わっても、ルールと記憶はリポジトリに残る。私は「AIを使う」から、
> 「AIチームを運営する」へ進んだ。

## 11. この依頼書の今後の更新ルール

Codexは新機能の実装を完了するたびに、次を自問します。

> この変化は、卒業制作図解へ反映すべきか。

次のどれかに当たる場合は、この依頼書も同じ作業で更新します。

- 情報源、監視件数、テスト件数などの数字が変わった
- 通知メールの見た目や操作が変わった
- 作品1または作品2の説明が変わる機能を追加した
- AIチームの役割、ルール、安全網が変わった
- 発表で伝える失敗、学び、方向転換が増えた

事実が食い違う場合の優先順位は、実装コードと`config.yaml`、本番ログ、`NEXT.md`、v1の
順です。確認できない数字は推測せず「要確認」と書いてください。
